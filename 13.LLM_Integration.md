# How LLM API Integration & Prompting Work

Everything practiced in the 11-phase plan lives inside the `messages`
field of an API call — the API itself is the plumbing that carries a
prompt to the model and back.

## Anatomy of an API Call

Every major provider's API takes roughly the same shape: an authenticated
POST request with a model name, a message history, and control parameters.

```javascript
const response = await fetch("https://api.anthropic.com/v1/messages", {
  method: "POST",
  headers: {
    "x-api-key": API_KEY,
    "anthropic-version": "2023-06-01",
    "Content-Type": "application/json"
  },
  body: JSON.stringify({
    model: MODEL_NAME,
    max_tokens: 1024,
    system: "You are a senior code reviewer. Flag security, performance, and readability issues.",
    messages: [
      { role: "user", content: "Review this code: ..." }
    ]
  })
});
```

### Field-to-phase mapping

| API field | What it controls | Which phase this is |
|-----------|-------------------|----------------------|
| `system` | Persistent role/persona, house rules for the whole session | Role prompting, Phase 7 |
| `messages` (role: `user`) | The actual task, few-shot examples, XML-tagged data | Phases 2–4 |
| `tools` | Tool definitions the model can call | Phase 8 |
| `max_tokens` | Hard cap on response length — also a direct cost lever | Phase 11 |
| `temperature` / `top_p` | Randomness — low for deterministic structured output, higher for brainstorming | Ties to Phase 6 |
| A JSON-schema or `response_format` param (provider-specific) | Server-enforced structured output | Phase 6 |

OpenAI and Gemini follow the same underlying shape — a `role`-tagged
message array, a system-level instruction field, and a tools/functions
parameter for tool use — with different field names and slightly
different conventions. Check each platform's current docs for exact
syntax since details evolve; the concepts transfer directly.

## The API Is Stateless — You Carry the Memory

The API has no memory between calls. Every request must include the
*entire* conversation history you want the model to see:

```javascript
messages: [
  { role: "user", content: "Write a function to flatten a nested list." },
  { role: "assistant", content: "[the model's earlier response]" },
  { role: "user", content: "Now handle the escaped-quote edge case too." }
]
```
The Phase 9 chain (generate, then feed the output back for review) is
literally this pattern: you hold the conversation together in your own
code, not the API.

## The Tool-Use Loop, Concretely

Phase 8 showed the concept; here's the actual request/response cycle:
1. You send a message + `tools` definition.
2. The model replies with a `tool_use` block instead of a final answer —
   no code runs on their end.
3. **Your code** executes the real function (hits an API, queries a
   database, whatever it is).
4. You send a *new* request with the tool's result appended as a
   `tool_result` message.
5. The model reads that result and produces the final natural-language
   answer.

This round-trip is the entire mechanism behind agents — an "agent" is
just this loop running multiple times in code.

## Streaming

Instead of waiting for the full response, you can request a stream: the
API sends the response as small chunks (server-sent events) as they're
generated — why chat UIs show text appearing word-by-word. Useful for
perceived latency in user-facing apps; irrelevant if you're just parsing
a final JSON object programmatically.

## Where Cost and Reliability Actually Come From

- **Cost** is billed per token — both input (everything in `messages`,
  including every few-shot example and the full chat history resent each
  turn) and output. This is why Phase 11's trimming exercise matters:
  every re-sent turn of history costs tokens again, every time.
- **Reliability** at the API level means handling rate limits (429
  responses) and transient errors with retries/backoff, and validating
  that structured output actually parses before trusting it downstream —
  a "JSON mode" flag doesn't guarantee code won't occasionally get
  something malformed.

Everything from Phase 1 through 11 comes down to: what goes in `system`,
what goes in `messages`, and which extra parameters (`tools`, schema
constraints, `temperature`) get set for the job at hand.
