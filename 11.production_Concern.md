#  Production Concerns (Final Phase)

## Concept
Three things separate a prompt that works in testing from one that holds
up in production: token efficiency, versioning discipline, and injection
guardrails.

## 1. Token Efficiency — Trim Without Losing Quality

### Original prompt
```
You are a senior code reviewer. Review the following code for three
categories: (1) security vulnerabilities, (2) performance issues,
(3) readability/naming. For each category, either flag a specific issue
or state "no issues found". Use this exact format:

Security: ...
Performance: ...
Readability: ...
```

### Trimmed prompt
```
Review this code for security, performance, and readability issues.
For each, state a specific issue or "none found". Format:

Security: ...
Performance: ...
Readability: ...
```

### Measured (character/word based approximation — sandbox couldn't reach
the real tokenizer vocab, so treat as directional, not exact)
```
Original: 305 chars, 44 words, ~76 tokens (approx)
Trimmed:  174 chars, 25 words, ~44 tokens (approx)
Char reduction: 43.0%
```
For real token counts, use each platform's own API token counter.

## 2. Prompt Versioning
- Keep prompt text in a file, not hardcoded inline in multiple places
- Track changes in git like any other code
- Tag which prompt version produced which eval results (ties back to
  Phase 10's scoring method)
- When behavior changes unexpectedly, check "did the prompt change?"
  before assuming the model changed

## 3. Injection Guardrails
Phase 3's lesson applied at scale: any time user input flows into a
prompt, wrap it in tags and explicitly state it's data, not instructions.
Validate/sanitize input before it reaches the prompt at all.
