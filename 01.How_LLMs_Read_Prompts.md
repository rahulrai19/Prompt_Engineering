## How LLMs Read Prompts

## Concept
Models don't weigh every part of a prompt equally. Instructions placed
immediately before the actual question tend to get followed more reliably
than the same instruction buried earlier in a long prompt — especially
formatting/output constraints. This matters whenever real prompts get long:
docs, retrieved context, pasted code, etc.

## Why it matters for developers
Any time you're stuffing context (docs, file contents, API specs) into a
prompt and expecting the model to still obey a formatting rule at the end,
instruction position can make or break reliability — especially for
structured output you plan to parse in code.

### Context block (used in both prompts)
```
The Pulsegrid API lets applications track and forecast small-scale energy
usage across connected IoT devices. Once a device is registered, Pulsegrid
begins polling it every 60 seconds and stores readings in a rolling
seven-day buffer. Developers can query historical readings, current device
status, and forecasted usage for the next 24 hours based on a simple
exponential smoothing model. The forecasting model recalculates whenever a
new day of data completes, and confidence intervals widen for devices with
fewer than three days of history. Pulsegrid also exposes a webhook system:
developers register a callback URL that fires whenever a device's usage
crosses a configurable threshold. Authentication uses short-lived bearer
tokens issued through a separate auth service, and every response includes
a rate-limit header. The API supports pagination on all list endpoints
using a cursor-based scheme rather than page numbers, avoiding the
duplicate-record problem page-number pagination has when records are
inserted mid-query. There are five main endpoint groups: device
registration and management, current status queries, historical reading
queries, forecast queries, and webhook management.
```
