# Tool Use / Function Calling

## Concept
You define a tool as a schema; the model decides whether to call it and
with what arguments. The tool's `description` field is itself a
prompt-engineering surface — as important as the JSON schema shape.

## Why it matters for developers
This is the foundation for anything agentic. A poorly described tool
either over-triggers (called for irrelevant queries) or under-triggers
(missed when it should apply) — exactly like a vague function name or
docstring misleads a human caller.

## Example Tool Definition
```json
{
  "name": "get_repo_info",
  "description": "Fetch metadata about a GitHub repository, including stars, open issues count, and primary language. Use this when the user asks about a specific named GitHub repo's stats.",
  "input_schema": {
    "type": "object",
    "properties": {
      "owner": { "type": "string", "description": "GitHub username or org that owns the repo" },
      "repo": { "type": "string", "description": "Repository name" }
    },
    "required": ["owner", "repo"]
  }
}
```

## Test Queries
- **Should trigger:** "How many stars does facebook/react have?" → expect a tool call with `{"owner": "facebook", "repo": "react"}`
- **Should NOT trigger:** "What's a popular JavaScript framework?" → expect a direct answer, no tool call

## Weakened Description Test
Re-run both queries with `"description": "gets data"` instead of the full
description, to see whether over- or under-triggering appears.
